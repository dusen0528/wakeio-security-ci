# 서브에이전트 운영 지침 (Codex 오케스트레이터용)

메인 Codex는 오케스트레이터이고, 서브에이전트는 **전체 기간 누적 역할 최대 10개, 동시 실행 최대 4개**로 운영한다.
서브에이전트는 코드워커 방식으로 일한다: 작업 패킷을 받아 자기 worktree에서 구현·테스트하고 **결과 요약만** 돌려준다.

## 1. 오케스트레이터만 하는 일

- `.handoff/` 요청서 작성과 `scripts/handoff/claude-review.mjs` 호출
- 마일스톤 브랜치 병합, 충돌 해결, `dev` PR 생성
- 작업 패킷 발행·재발행, 역할 간 공유 파일 변경 승인
- 보호 파일 반영(사람이 준 수정본을 `[handoff-update]` 커밋으로만)

서브에이전트는 위 일을 하지 않는다.

## 2. 역할 (최대 10)

| ID | 역할 | 쓰기 소유 경로 | 주 마일스톤 | 금지 |
| --- | --- | --- | --- | --- |
| R1 | 계약·레지스트리 | `src/runtime/types.ts`, `src/runtime/registry.ts`, 신규 `schemas/*.json`, `src/agent-dast/plan.ts`의 엔진 디스패치, `src/agent-provider.ts` 확장 | M0~M5 | 다른 역할 구현 파일 수정 |
| R2 | 정적 분석 레지스트리 | `src/source.ts`의 도구 디스패치, `src/source/code-coverage.ts`, AnalyzerProvider 어댑터 | M0, M5 | 기존 도구 출력 문구·순서 변경 |
| R3 | 빌드·런타임 | `src/runtime/builders/**`, `src/runtime/runtimes/**` | M1~M3 | 격리 정책 완화 |
| R4 | 표면 발견 | `src/runtime/surfaces/**`(workflow 제외), `src/init-dast.ts`의 v2 확장 | M1, M3 | Inventory v1 출력 변경 |
| R5 | 관측·주입 판정 | `src/runtime/observers/**`, `src/runtime/markers.ts`, `src/runtime/oracles/{sql,command,ssrf,path,xss,redirect}.ts` | M1~M2 | 고정 예제·기대 판정 수정 |
| R6 | 권한 판정 | `src/runtime/oracles/authz.ts`, `src/runtime/accounts.ts`, API 정책 v2 재사용 어댑터 | M2 | `scan`의 API 정책 동작 변경, 고정 예제 수정 |
| R7 | 워크플로 발견 | `src/runtime/surfaces/workflow.ts`, Inventory v2 `sequences` | M3~M4 | 판정 로직 수정 |
| R8 | 고정 예제·코퍼스 (독립 작성자) | `examples/runtime/**`, `benchmarks/runtime-corpus.json`, 기대 판정 파일 | M1~M5 | 제품 코드(`src/**`) 수정 |
| R9 | 검증·증거 (실행자) | `.handoff/evidence/**`, `.github/workflows/runtime-*.yml` | 매 체크포인트 | 제품 코드·테스트 기대값 수정 |
| R10 | 보고서·CLI·사용자 문서 | `src/report.ts`의 runtime 섹션, `src/cli.ts`의 `verify`·`init-target`·`doctor --runtime` 배선, 사용자 문서 | M1~M5 | 기존 `scan` 보고서·종료 코드 변경 |

- `src/contracts.ts`, `src/report.ts`, `src/cli.ts`는 공유 핫스팟이다. 소유자(R1, R10) 외에는 "공유 파일 변경 요청"으로만 바꾼다.
- 역할 수가 10을 넘는 작업이 생기면 새 역할을 만들지 말고 기존 역할에 패킷을 추가한다.

## 3. 독립성 규칙

- **예제와 구현의 분리:** R8의 고정 예제와 기대 판정은 Oracle 구현자(R5, R6)가 바꿀 수 없다. 기대값을 바꿀 때는 R8이 이유를 적고 오케스트레이터가 승인하며, 다음 리뷰 요청서에 명시한다.
- **증거의 분리:** 검증 결과와 증거 파일은 R9만 만든다. 구현 역할의 자체 테스트 결과는 참고용이다.
- **판정의 분리:** LLM 기반 역할이나 에이전트 코드는 Oracle 판정 결과를 바꾸는 경로를 가지지 않는다.

## 5. 작업 패킷 형식 (오케스트레이터 → 서브에이전트)

```text
TASK <M번호>-<순번> / 역할 R<n>
목표: <한두 문장>
PLAN 참조: <장·절>
브랜치: codex/rv-m<N>-<slug>--r<n>-<짧은이름> (마일스톤 브랜치에서 분기한 별도 worktree)
쓰기 가능 경로: <목록>
읽기만: <목록>
금지: <목록 + 공통 안전 규칙>
완료 조건: <테스트 파일·명령·기대 결과>
상한: 변경 <N>줄 이내, 같은 실패 2회 시 blocked로 반환
반환: 6절 형식
```

## 6. 결과 형식 (서브에이전트 → 오케스트레이터, 20줄 이내)

```text
상태: done | partial | blocked
브랜치 / 커밋: <SHA 목록>
변경 파일: <경로 (+줄/-줄)>
실행한 검증: <명령 → exit, 통과/실패/건너뜀 수>
PLAN과 다른 결정: <내용과 이유, 없으면 없음>
공유 파일 변경 요청: <경로와 바꿀 내용, 없으면 없음>
미해결 질문: <없으면 없음>
```

전체 로그나 긴 diff는 결과에 붙이지 않는다. 오케스트레이터가 필요하면 브랜치를 직접 본다.

## 7. 병합 순서

1. R1(계약·타입·스키마)을 먼저 병합한다. 다른 역할은 병합된 계약을 기준으로 리베이스한다.
2. 구현 역할(R2~R7)을 의존 순서대로 병합한다.
3. R10(보고서·CLI 배선)을 병합한다.
4. R8 고정 예제가 기대 판정대로 통과하는지 확인한다.
5. R9가 전체 테스트, compat-0.5, KPI compare, 증거 정리를 끝낸 뒤 체크포인트 요청서를 쓴다.

의미 충돌(계약 위반, 다른 역할 경로 침범)은 오케스트레이터가 고치지 말고 해당 역할에 패킷을 재발행한다.

## 8. 체크포인트와의 연결

- **CP1 요청서:** 이번 마일스톤의 패킷 목록(역할, 쓰기 경로, 완료 조건)을 첨부한다. 리뷰어가 경계 침범을 사전에 볼 수 있게 한다.
- **CP2 요청서:** 모든 패킷 병합과 R9 검증이 끝난 뒤 낸다. 패킷별 결과 요약 표를 붙인다.
- **리뷰 blocking 항목:** 해당 경로의 소유 역할에 패킷으로 재발행하고, 다음 요청서에 B번호 → 패킷 → 커밋 SHA를 적는다.

## 9. 공통 안전 규칙 (모든 서브에이전트)

- 대상 코드 빌드·실행과 Docker 실행은 소유 고정 예제(`examples/runtime/**`)와 `verify --execute-target-consent` 경로에서만 한다. 외부 호스트를 검사 대상으로 삼지 않는다.
- 비밀값·토큰·계정 정보를 로그, 결과, 증거, 커밋에 남기지 않는다.
- 테스트·임계값·기대값을 완화해서 통과시키지 않는다.
- 보호 파일, `.handoff/*.response.*`를 수정하지 않고 리뷰 래퍼를 호출하지 않는다.
- 새 코드는 한 줄 120자, 한 함수 60줄 이내를 기본으로 한다.

## 10. 비용·중단

- 패킷 상한(변경 줄 수, 같은 실패 2회)을 넘으면 `blocked`로 반환한다.
- 오케스트레이터는 blocked 패킷을 쪼개 재발행하거나, 설계 문제면 다음 요청서의 "미해결 질문 / PLAN 변경 제안"으로 올린다.
- 동시 실행 4개를 넘기지 않는다. 리뷰 대기 중에는 새 구현 패킷을 발행하지 않는다.
