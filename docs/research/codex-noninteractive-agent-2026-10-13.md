# Codex non-interactive agent integration: narrow proposal (2026-10-13)

## Decision

Add an **explicit, report-only advice command** to the 0.5.0 source preview. It should consume a completed, redacted `agent-report.json`, invoke the user-selected Codex CLI in non-interactive mode, and write a separate `agent-advice.json`. Advice must never change the original scan gate, a finding's verification state, or the scan exit code. Keep the existing SQL injection `repair` workflow separate. Do not make a model necessary for the free local `scan` path. Other providers can be an explicitly selected later adapter, with no automatic fallback.

This is feasible as a bounded local feature. The repository already has process supervision and a Codex proposal adapter, and the installed CLI and current official documentation expose the required non-interactive and structured-output interfaces. The sections below record the initial research boundary; the implementation and live-check outcome are recorded at the end.

## Existing product boundary

- [`src/cli.ts`](../../src/cli.ts) dispatches `scan`, `plan`, `compare`, `replay`, `repair`, and other commands independently. `scan` writes four reports and applies its own scan gate. Add an independent command (working name `advise`) rather than triggering Codex during `scan` or reusing `repair`'s exit statuses.
- [`docs/agent-report.md`](../agent-report.md), [`src/contracts.ts`](../../src/contracts.ts), and [`src/report.ts`](../../src/report.ts) already define the redacted, versioned projection: `scanGate`, summary, checks, findings, source scope, `reportArtifact.digest`, and consumer requirements. It declares finding `verification.state = not_run` and remediation `state = not_verified`. The digest binds the emitted `report.json` bytes, but the four-file delivery is only per-file atomic; neither the digest nor a gate alone is a CI success receipt.
- [`src/repair.ts`](../../src/repair.ts) already offers opt-in `--agent codex|claude --allow-source-upload` for a *different* job: produce SQL replacement content after a frozen vulnerable baseline, then test a copy in a bounded Docker verifier. Its `repair.json` and `changes.patch` are private and do not rewrite `agent-report.json`.
- [`src/repair-provider.ts`](../../src/repair-provider.ts) already supplies the useful adapter pattern: executable resolution, `exec --help`/version checks, a private working directory, JSON Schema, `--json`, `--output-last-message`, `--ephemeral`, `--ignore-user-config`, `--ignore-rules`, read-only sandbox, disabled feature list, and event rejection for tool calls. [`src/source/process.ts`](../../src/source/process.ts) launches argument arrays without a shell, builds a minimal environment, bounds output and deadline, and signals the owned process group on timeout. Reuse and harden these primitives; do not duplicate an arbitrary shell-command interface.

## Current documented and observed Codex interface

The [official non-interactive guide](https://learn.chatgpt.com/docs/non-interactive-mode) says `codex exec` is for scripts and CI; `--json` emits JSONL events including `turn.failed`, `error`, and tool items; `--output-schema` requests a final JSON Schema response; `-o` stores the final message; and `--ephemeral` avoids session rollout persistence. It describes read-only sandbox as the default and documents `--ignore-user-config` and `--ignore-rules`. The [developer command reference](https://learn.chatgpt.com/docs/developer-commands?surface=cli) documents the same options, prompt on stdin via `-`, and `--skip-git-repo-check` for a private directory outside Git. OpenAI also identifies `codex exec` as the script/one-off integration layer in its [Codex harness article](https://developers.openai.com/blog/codex-as-a-platform).

Local read-only inspection on 2026-10-13: `command -v codex` resolved to `/Applications/ChatGPT.app/Contents/Resources/codex-cli/CodexCLI.app/Contents/MacOS/codex`; `codex --version` reported `codex-cli 0.162.0-alpha.17.2`. `codex exec --help` listed all of the existing adapter's checked option names, including `--ignore-user-config`, `--ignore-rules`, `--strict-config`, `--skip-git-repo-check`, `--ephemeral`, `--sandbox`, `--disable`, `--output-schema`, `--output-last-message`, and `--json`. `codex features list` listed its disabled feature names, including `shell_tool`, `unified_exec`, `apps`, `plugins`, `hooks`, `browser_use`, `computer_use`, and `multi_agent`. This establishes local option/name presence, **not** successful execution or complete runtime isolation. An alpha CLI can change; retain runtime checks and fail closed.

The existing `CODEX_API_KEY` requirement is **current**, not a stale flag. The [official environment-variable reference](https://learn.chatgpt.com/docs/config-file/environment-variables) identifies it for non-interactive exec, and the [non-interactive guide](https://learn.chatgpt.com/docs/non-interactive-mode#use-api-key-auth) shows inline use. The same guide describes ChatGPT-managed account auth for trusted runners as an advanced path and warns that `auth.json` contains access tokens. The command reference says `--ignore-user-config` skips config but still uses `CODEX_HOME` for auth. In this repository, the private `HOME` plus minimal environment intentionally keep user Codex state out of the provider child and require `CODEX_API_KEY`; simply assuming a signed-in desktop app will authenticate the isolated child would be incorrect. Do not read, copy, print, or persist credential files to work around that. If account-auth reuse becomes a user requirement, design and test it as a separate trust boundary.

## Narrow implementation contract

1. Accept only `advise --report <agent-report.json> --out <new-private-directory> --agent codex --allow-report-upload` plus a bounded timeout and optional reviewed executable path. Naming can change, but report upload and provider selection must be explicit. Never accept a shell command string, repository root, source path, arbitrary file list, or target URL for the model to explore. No automatic Claude/model fallback.
2. Read the report as a bounded, no-symlink regular JSON file. Verify `schemaVersion`, exact expected envelope shape/field types needed by the advisor, bounded findings/check counts and text, and scan/verification semantics. Re-read the sibling `report.json`, hash its exact bytes, and require equality with `reportArtifact.digest` before sending. This detects a mismatched or partial report pair; it does not prove CI process delivery. Reject unsupported versions rather than inventing defaults. Treat descriptions, notes, remediation prose, and references as **untrusted data**, even though the producer sanitised common secrets.
3. Build a small structured prompt from allow-listed report fields: gate and reason codes, declared scope, selected check status/gaps, finding IDs and bounded evidence/navigation. Prefer a capped projection over uploading the full report. Omit raw source, arbitrary paths/URLs, scanner logs, and instruction-looking content that has no diagnostic value. Show the exact data categories and outbound-upload boundary in command help. The prompt should ask for prioritised *review steps and uncertainty*, no exploit or verified-fix claim.
4. Reuse `runProcess` and the Codex branch of `providerProposal` only after extracting a generic structured-exec helper; preserve the private cwd/HOME, minimal env and explicit `CODEX_API_KEY`, argument-vector spawn, shared deadline, output cap, process-group termination, and `--ignore-user-config --ignore-rules --strict-config --ephemeral --sandbox read-only --skip-git-repo-check --json --output-schema ... -`. Disable shell/exec, web, app, MCP/plugin, hook, browser, and subagent affordances as far as the installed CLI documents and verifies. Set a noninteractive approval policy; fail if a required policy option is unsupported. A prompt saying “do not use tools” or rejecting tool events *after* execution is insufficient to prevent a side effect. A process sandbox/container is needed before claiming hard isolation; report-only advice can instead have a narrowly scoped, explicit no-tool policy and refrain from a hard isolation claim.
5. Parse JSONL incrementally with a line/byte limit. Require one `thread.started`, one `turn.started`, one `turn.completed`, no `error`/`turn.failed`, no tool-item event, successful process exit and completed cleanup before trusting the bounded final-message file. Validate the final JSON locally against a strict schema and against the *input* report: referenced finding IDs/check indexes must exist; action verbs cannot silently become executed actions; summary counts and scan gate remain copied from the report, never model-generated. On any mismatch, timeout, output cap, or unknown event, write only a fixed incomplete/error receipt without model prose.
6. Write `agent-advice.json` (and optionally Markdown rendered from validated fields) into a new private directory; include input report SHA-256, linked `report.json` digest, provider name/version/binary hash, policy version, requested model or `unknown`, outcome, and explicit `verified: false`. No `report.json`/`agent-report.json` rewrite, scan gate alteration, patch, commit, PR, or source collection of advice artifacts. Keep model text bounded and clearly labelled advice. A successful advice command means the advice artifact was produced, **not** a scan pass or vulnerability/remediation verification.

The [official security guidance for self-hosted agent environments](https://developers.openai.com/api/docs/guides/agents-api/environments/security) notes that agent-generated code can access available files, credentials and network; thus feature toggles and a read-only sandbox should not be presented as a universal data-isolation guarantee. This note's recommendation is deliberately data-only and cannot establish that arbitrary sensitive prose in a report was redacted.

## Concrete gaps to resolve while implementing

| Current behavior | Consequence for report advice |
| --- | --- |
| `providerProposal` schema is replacement paths, hashes, and full file content | Needs a separate advice schema; reusing repair output would conflate triage and patching. |
| It checks help text and feature names, then rejects tool events only after `codex exec` exits | Necessary fail-closed parsing, but not preventive isolation; keep the child without access to source/user config and do not claim that event checks stopped a tool call. |
| `runProcess` provides group signalling but the ordinary lane does not expose strict `cleanupConfirmed`/RSS observation | A timeout must not be reported as cleanly terminated unless cleanup is confirmed; adapt the existing strict supervision or record cleanup uncertainty for the agent lane. |
| The Codex branch requires `CODEX_API_KEY`; `--ignore-user-config` still leaves auth attached to `CODEX_HOME` | Private HOME and minimal env mean existing app login is not automatically reused. Do not advertise account-based execution until explicitly built and tested. |
| Agent report sanitisation is pattern-based; text fields may retain arbitrary private prose | Explicit outbound consent, capped projection, and user review of upload categories are still required. |
| Official JSONL has failure/error and tool item variants; current parser only accepts a small success subset | For advice, validate a complete successful event sequence and failure modes; preserve unknown-event fail-closed behavior. |

## Verification ladder

Before any live model use: typecheck/build, CLI help and invalid-input tests, report/digest mismatch and symlink rejection, malicious report prose, unknown finding IDs, malformed/extra JSONL events, timeout/output-cap/child-group cleanup, missing key, and a fake Codex executable protocol fixture. Confirm default `scan` output and exit status are byte-for-byte unaffected. The existing mock provider test is useful but proves only the mock protocol, not Codex model behavior.

If a live call is included in the authorised implementation phase, the smallest useful smoke test is **one explicitly opted-in Codex invocation against an owned synthetic `agent-report.json`**, with an already provisioned API-key environment and no source text or secrets. Record only status, version, schema acceptance, whether any tool event appeared, output bounds and artifact semantics; never print a credential or raw reasoning trace. A live test on real customer source/report, desktop account-auth file reuse, installation/release, or billing claim is outside this research verification.

## Implementation and observed result (later on 2026-10-13)

The user selected **both** explicit authentication modes, so the implemented [`advise`](../agent-advice.md) command supports `--auth cli-login` and `--auth api-key`; there is no implicit fallback. The local-login mode gives the native CLI the `CODEX_HOME` directory path without Wakeio reading or copying credential files. The API-key mode forwards `CODEX_API_KEY` only to the selected child. A separate supervised process lane requires confirmed owned process-group cleanup, and the JSONL parser rejects every tool/error event. The output schema and local validation bind recommendations to input finding/check IDs or `scope`. Atomic, no-clobber publication keeps advice separate from scan truth.

The installed Codex 0.162.0-alpha.17.2 emitted a pre-turn error when `code_mode_host` was explicitly disabled. Its `features list` shows `code_mode=false` and `code_mode_host=true` by default; the bundled binary describes `code_mode_host` as a prerequisite for Code Mode host infrastructure. The advisor leaves that host feature at its default while explicitly disabling agent-facing `code_mode`, shell/unified execution, shell snapshots, browser/computer use, plugins, hooks, and related capabilities. No error event is ignored. A live run on the owned native SQLite demonstration's redacted vulnerable report then exited 0 with four clean events, three validated recommendations, `verified:false`, and a digest-linked private advice artifact. This proves only that specific CLI-login interaction and owned synthetic input. The API-key mode passed fake-CLI tests; no `CODEX_API_KEY` was present for a live API-key call. No billing cap or hard filesystem/network isolation was established.
