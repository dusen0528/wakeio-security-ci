## Frozen semantic matrix

1. **Worker completion and privacy.** A completed worker result has a nonempty declared plan, every planned check executed, skipped0, gaps0 and truncationfalse. Missing work, all-zero plan, skipped/error work, gaps or truncation cannot be completed. Counts remain descriptive claims until reconciled with trusted execution/store records. Valid completed and explicit partial/error results are positive controls. Unknown JSON keys containing token/body canaries at every object depth yield only fixed rejection reasons/paths; keys and raw stdout are never echoed. SDK object validation rejects getters, proxies, custom prototypes and callable inputs without firing caller code. A successful parse binds run/task/category to the assigned identity.
2. **Declared coverage, assignment and retained history.** New tasks predeclare a nonempty `coveragePlan:[{surfaceId,check}]`; every surface exists in the same run and is assigned to that task. Only a running task inside a running run may append its planned coverage or finding observation. Cross-run, unassigned, missing and unplanned check rows are rejected with no database mutation. Exact repeated coverage is idempotent; conflicting executed/skipped/error outcomes or reasons cannot overwrite prior evidence. Confirm this on actual memory and disk SQLite with an independently owned row-state oracle, not merely exception messages or product summary labels.
3. **Trusted completion and run sealing.** A completed task needs the actual complete nonempty plan recorded as executed, worker coverage/finding IDs/severity counts consistent with persisted observations, and a trusted matching-provider successful bounded ledger. Missing rows, skipped/error rows, lying worker counts, wrong provider, nonzero/missing exit, invalid/oversized stdout, truncation or contradictory ledger leave the task running/incomplete and preserve all earlier data. A run may complete only after all its tasks completed; pending/running/partial/error/skipped work cannot become a completed run. A terminal run/task accepts no late writes or repeated transition. Positive control: coherent full plan + successful ledger completes and remains stable after reopening.
4. **Context-sensitive deduplication with severity/evidence retention.** Findings with the same rule/method/normalized path/parameter in the same auth and parameter-location context may deduplicate. Different auth states or parameter locations remain distinct. Every task's observation/evidence identity is retained even when a finding deduplicates; later stronger severity must raise the retained aggregate severity. Confirmed findings retain their severity in the relevant summary. A later observation must not disappear behind an earlier rejected state. Low-then-high and high-then-low produce the same strongest result; workers sharing one deduplicated finding still have independently checkable observations. Candidate/confirmed/rejected are evidence states, not independent exploit or remediation proof.
5. **Atomic failure, fallback and lifecycle.** Mixed valid+invalid batches and failed task closure roll back every write made by that operation, including task status, gaps and ledger, while preserving prior accepted findings/coverage. Runner error fallback cannot complete a task or run and cannot erase database findings already recorded. Actual SQLite constraint/transaction faults must fail coherently, leave a usable store and not produce a misleading completed summary. Disk reopen must preserve identities, coverage outcomes and observation severity/evidence. Mutable caller input cannot alter stored history after an accepted call.
6. **Old database and distribution boundaries.** A populated prototype-v1 database may be explicitly refused without changing its bytes; silently inventing coverage plans/observations is forbidden. New store version/schema must be declared. Fresh supported empty stores work; unsupported/corrupt databases fail without an invented clean result. Root will check internal module and reference worker JSON-schema availability from fresh npm/source archives, Node SQLite version failure and unchanged existing CLI/report behavior. Schema presence is not CLI integration or worker attestation.

- Add an unknown property named by an owned secret canary to an otherwise valid result; verify baseline rejection reflects that name in `path`. Pair with valid parse and ordinary fixed-field rejection.
- Create two runs with tasks/surfaces; baseline `recordCoverage` accepts a run-A task/run-B surface and overwrites an earlier error outcome with executed. Independently query actual SQLite rows. Candidate must reject and preserve before-state.
- Record low then high under one baseline dedupe key; baseline keeps the first severity and hides later observation identity. Candidate retains maximum severity and both task observations, with separate auth/location contexts as positive distinct controls.

Each assertion is frozen from these source-level failures and the adopted contract. A candidate's label or passing fixture count cannot define the oracle. Public API names and additive schema details may be filled in before the first execution when producer confirms them; semantic outcomes above will not be weakened to fit implementation. Expected baseline rejection of newly required fields is missing-capability evidence, not proof that the original four defects were corrected.
