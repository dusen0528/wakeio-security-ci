# OpenAPI and API session automation completion plan (2026-10-20)

User: WakeIO CLI/CI users with approved disposable API targets. The current 442069d implementation requires handwritten seeds, supports a static Authorization value and one JSON field, and has only a six-site self-authored pilot. The goal is importing approved local OpenAPI operations, automating API login/session renewal and measuring a representative application pair without weakening request accounting.

## Decisions and alternatives

1. Use the upstream OpenAPI job and JSON/form authentication context through the existing Node relay. Project the selected OpenAPI operations into a local virtual-origin definition; never import an arbitrary remote URL or use document server authority. Credentials and live session values remain Node-only, with synthetic engine session aliases. This reuses native generation/authentication and the existing admission/report/store contracts.
2. Controller-only generated seeds would be simpler but would leave the requested upstream jobs unconnected. Direct native HTTPS/credential forwarding would hide requests in CONNECT or expose session material to engine state. Neither meets this task's boundary.

## Executable stages and checks

1. Add a version-2 policy, same-document OpenAPI reference reuse, selected GET/query and POST/JSON compilation, bounded nested objects/arrays, concrete path parameters, source/projected-definition digests. Keep version 1 and existing aliases compatible. Verify rejected external/cyclic refs, wrong origins, unsupported operations and invalid schemas cause zero requests.
2. Run the pinned upstream `openapi` job on the generated local definition. Flatten selected JSON scalar locations into deterministic engine aliases, reconstruct only the validated target body in Node, and bind findings back to JSON pointers. Verify actual nested/array SQLi and fixed counterparts, no extra properties/methods/paths and unchanged total wire accounting.
3. Add declarative JSON/form login, cookie or Bearer session extraction, optional explicit refresh endpoint and bounded attempts. Drive upstream JSON/form user authentication using synthetic credentials/session cookies at a private virtual endpoint. Node performs the actual login/refresh under the same cap/rate/deadline; real credentials/tokens/cookies never enter ZAP plans/environment or normalized artifacts. Verify identity before/after and anonymous denial, expiry/renewal, wrong credentials/principal, transport loss, scope, budget and cancellation. Interactive browser/MFA/OAuth-provider automation is not part of the API profile.
4. Keep CLI, run-plan, the two existing Actions, offline preflight, four reports, DB evidence/surface identity and fail-on/incomplete gates connected. Verify actual engine execution through bundled and installed paths, including HTTPS CA/hostname validation and global ZAP/native admission.
5. Expand evaluation: a real login/refresh/search reference API with SQLite and nested JSON, and an upstream-pinned OWASP Juice Shop container restricted to owned loopback targets with a reviewable SQL fix. Freeze labels and source/patch digests before repeated runs. Report per-target TP/FP/FN/TN, denied/unexecuted scope, every login/refresh/control/probe request and full elapsed time. Retain misses and incomplete results; do not tune labels to results or infer production accuracy.
6. Run targeted regressions, actual pinned ZAP checks, the complete required-engine zero-skip suite, CI contracts, package/install smoke and remote CI. Commit implementation/evidence and update PR #76 around the final behavior. No tag/publication/deployment/merge is authorized by this step.

## Acceptance

- A v2 imported policy works through scan, run-plan and both Actions; v1 tests remain green.
- Login/refresh/probes share one exact request admission; any unresolved failure is exit 2 even with fail-on none.
- The engine receives only synthetic authentication values and a sanitized local OpenAPI definition; actual request/evidence artifacts contain no credential or raw-body disclosure.
- Nested and array findings preserve distinct rule/method/path/JSON-pointer identities and the DB → evidence → engine finding → report chain.
- Repeated paired application measurements are reproducible with predeclared ground truth, recorded scope and honest misses; the old six-site pilot is not presented as representative evidence.
- Required-engine tests have zero failures/skips, final package works after installation, and final SHA/CI status is reported.

Spec self-review: the upstream job's maxMessages is a soft import limit, so enforcement remains the gate; a synthetic auth exchange is distinct from a real target attempt. There is no remote schema fetch, automatic target launch during scan, arbitrary policy/script authority or implicit external target permission. All benchmark provisioning is explicitly owned and loopback only.
